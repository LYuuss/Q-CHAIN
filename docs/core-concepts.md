# QChain Core Concepts

QChain is an experimental Proof-of-Work blockchain built from scratch in Python.

It implements blocks, headers, Merkle roots, wallets, signed transactions, a mempool, transaction fees, dynamic difficulty adjustment, orphan blocks, side-branch fork management, automatic reorganization, header-first synchronization, and the heaviest-chain rule.

---

## Blocks

Each block contains:

```text
Block
├── header
│   ├── index
│   ├── previous_hash
│   ├── merkle_root
│   ├── difficulty
│   ├── timestamp
│   └── nonce
├── hash
└── transactions
```

The block hash is computed from the header. Transactions are summarized through the Merkle root.

---

## Proof of Work

A miner must find a nonce such that the block hash starts with a number of zeroes.

Example:

```text
difficulty = 4
valid hash = 0000a93f...
```

---

## Dynamic Difficulty

QChain adjusts difficulty using:

```text
target block time = 10 seconds
difficulty adjustment interval = 5 blocks
minimum difficulty = 1
maximum difficulty = 8
```

---

## Transactions

A transaction contains:

```text
sender
receiver
amount
nonce
fee
signature
```

The sender pays:

```text
amount + fee
```

The receiver gets:

```text
amount
```

The miner gets:

```text
block reward + total fees
```

---

## Coinbase Transactions

A coinbase transaction is generated by the protocol when a miner mines a block.

```text
sender = COINBASE
receiver = miner address
amount = block reward + total fees
```

Current block reward:

```text
50 QCOIN
```

---

## Wallets and Signatures

Wallets contain a private key, public key, and address. Wallet files are stored in:

```text
data/wallets/
```

The current implementation uses Ed25519 signatures through the `cryptography` package. This is a classical placeholder while the project evolves toward post-quantum signatures.

---

## Mempool

The mempool stores pending valid transactions before they are mined.

When a transaction is received:

```text
verify signature
check balance
check nonce
add to mempool
broadcast to peers
```

When a transaction is mined, it is removed from the mempool.

---

## Orphan Blocks

An orphan block is a block whose parent is missing locally.

Example:

```text
local node knows:
0 -> 1

node receives:
block 3

but block 2 is missing
```

QChain stores it temporarily in the orphan pool.

```text
MAX_ORPHAN_BLOCKS = 100
```

Endpoint:

```text
GET /orphans
```

CLI:

```bash
python3 src/qchain.py node-orphans 5001
```

The node retries orphan blocks after receiving a block, mining a block, or synchronizing.

---

## Side-Branch Fork Management

A side branch is a valid competing branch whose parent is known, but which does not extend the current main chain tip.

Example:

```text
main chain:
0 -> 1A -> 2A

side branch:
0 -> 1B
```

Block `1B` is not an orphan because its parent is known. It is stored in the side-branch pool.

```text
MAX_SIDE_BRANCH_BLOCKS = 200
```

Endpoint:

```text
GET /side-branches
```

CLI:

```bash
python3 src/qchain.py node-side-branches 5001
```

Normal output:

```json
{
  "blocks": [],
  "max_size": 200,
  "size": 0,
  "tip_hashes": []
}
```

---

## Automatic Reorganization

A reorganization happens when a side branch becomes better than the current main chain.

Example:

```text
current main chain:
0 -> 1A

side branch:
0 -> 1B -> 2B
```

If the side branch has more cumulative work, QChain can adopt it.

Process:

```text
find side-branch tip
walk backward through side-branch blocks
find common ancestor in main chain
build candidate chain
validate candidate chain
compare cumulative work
adopt if better
```

This gives QChain a first real fork-management layer.

---

## Heaviest-Chain Rule

QChain uses cumulative work to select the best chain.

The best chain is not necessarily the longest chain. It is the chain with the most accumulated Proof of Work.

---

## Header-First Synchronization

Previous model:

```text
GET /chain
download full peer chain
validate
adopt if heavier
```

Current model:

```text
GET /status
GET /headers
validate headers
find common ancestor
GET /blocks/<hash> for missing blocks
rebuild candidate chain
adopt if heavier
process orphan blocks
process side branches
```

If the node is already synchronized:

```text
downloaded_block_count = 0
```

---

## Block Reception Cases

QChain distinguishes:

```text
direct extension:
    accepted into main chain

missing parent:
    stored as orphan

known parent but not current tip:
    stored as side branch
```
